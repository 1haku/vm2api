套餐周额度支持选择「独立周期」或「跟随指定槽位的官方周窗口」。独立迁移 `005_official_weekly_window.sql` 只增加默认 independent 与空窗口字段，旧套餐、额度、用户和账本保持原值。新模式要求参考槽位属于该套餐且为同平台公共槽位，并已获取有效官方 7d 总窗口；不使用 5h 或模型专用窗口。多人共享时间边界但单独计费，切换后按官方当前周重新汇总历史账本，保留手动清零截断，不主动清空额度。手动重置仍清零日/周用量，但不移动官方边界；续期不改变周期。日额度仍在北京时间 00:00 重置。

官方窗口信息通过既有账号快照读取并持久化：当前窗口内未取得新数据时沿用已确认边界，到期后若尚无下一窗口则返回等待同步，并对限周额度请求返回 `subscription_window_pending`；管理员在槽位页查询限额即可补全。换号、槽位丢失不会静默套用旧账号周期；重新查询并保存方案后才采纳新账号。当前窗口的截止时间调整不会清零已用金额；跨窗口迟到结算按实际结算时间归入新窗口，进行中预留持续计入。普通用户只看到周期类型、同步状态和时间，不暴露参考账号标识。回滚须使用升级前配套数据库备份。

面板登录支持 Cloudflare Turnstile。服务器 `.env` 配置 `TURNSTILE_ENABLED=1`、`TURNSTILE_SITE_KEY`、`TURNSTILE_SECRET` 和逗号分隔的 `TURNSTILE_HOSTNAMES`（只填允许的前端域名，不填协议/端口/路径）。Secret 不放进源码、前端、日志或公开配置。`GET /api/panel/login-config` 只返回启用/就绪状态、公开 Site Key 和允许域名；登录服务端固定向官方 Siteverify 验证，强制 success=true、action=login 及域名匹配，8 秒超时拒绝登录。每次失败后重新获取一次性 token。使用居中登录卡片，内网 IP 访问提示改用允许域名，不按 Host/转发头/内网 IP 绕过。

登录限流独立于 Turnstile：每账户 10 次/10 分钟、每 socket 来源 60 次/分钟、全站 300 次/分钟，按窗口恢复，进程内存储且有容量上限。Tunnel 客户端可能共用一个来源，不信任任意转发 IP 头。验证服务故障不自动放行；管理员可通过 SSH 将服务器 `.env` 的 `TURNSTILE_ENABLED=0` 后执行 `docker compose up -d --no-deps vm2api` 恢复密码登录。模型 API、已登录会话、订阅和计费不增加人机验证。无数据库迁移。

## 数据库迁移

### 独立手动日重置

管理员在订阅列表可选择「重置日额度」或「重置日/周额度」。日重置使用 `PATCH /api/panel/subscriptions/:id`，请求体为 `{ "action": "reset_daily" }`，普通用户无权执行。它仅清零该用户该套餐的日用量，保留周用量、日/周重置时间、有效期和消费历史；正在进行的请求正常结算，不清除预留。操作日志记录 `reset_daily` 和操作者。

定制迁移 `006_daily_quota_reset.sql` 增加 `daily_quota_reset_at` 和 `daily_reset_ledger_rowid`，原记录默认 NULL/0，不改写旧账本。日用量同时遵守自然日、周窗口、整体手动重置和独立日重置边界，并用账本顺序处理同毫秒的重置/结算。原 `reset` 动作仍清零日/周用量：独立周模式重新起算 7 天，跟随官方模式保留官方周截止时间。

上游继续使用 `src/lib/db/migrations` 和 `schema_migrations`；定制功能使用 `src/lib/db/custom-migrations` 和 `custom_schema_migrations`，版本号独立。后续定制 SQL 新增编号文件，不修改已经应用的文件。

v1 的 `027_subscriptions.sql` 在 v2 改为定制 `001_subscriptions.sql`。升级时先验证旧迁移文件名与内容校验和，再把记录移到定制表，不重复执行 SQL、不删除业务数据。后续上游的 027 可以正常使用。命名空间隔离不会自动解决同名表、列或行为上的冲突，仍须审查上游变更。

v4 新增 `002_subscription_namespace.sql`，原已发布的 001 完全不变。7 张业务表统一采用 `custom_` 前缀，日/周额度、默认期限和订阅并发移入 `custom_subscription_plans`。`groups` 上旧扩展字段作为历史兼容数据保留，定制代码不再依赖它们；方案名称/平台/状态仍关联上游 groups，`usage_logs.subscription_id` 也仍是扩展列。因此降低了合并冲突范围，但不能保证未来 main 的任何改动都兼容。

账本采用显式整数主键，手工重置记录账目顺序边界，解决同一毫秒结算与重置的歧义；VACUUM 不改变该顺序。账目只追加，不通过删除历史记录恢复额度。

`node scripts/check-subscriptions-upgrade.mjs <数据库副本路径>` 会在副本执行迁移，验证 SQLite 完整性、外键、迁移版本，并比较用户、Key、槽位、订阅、配置额度、预留、账本、响应归属和请求记录的规范化内容摘要。报告只含计数和摘要，不输出凭据。上游如果有意变更这些数据，预检会中止，需要审查并明确调整比较规则，不能仅因行数相同就放行。

## 当前部署与回滚

### 自动保留最近三份

同时清理本项目未被容器引用、没有标签的构建中间镜像，通过镜像内 package.json、Go 模块名或 payload 仓库字段识别项目；检查时只创建未启动的临时容器并读取标识文件，不执行镜像代码，不做全局 image/volume prune。沿已识别缓存的父层向上回收，只有全部子层均属待清理缓存时才继续；遇到带标签、容器使用或其他项目分支即停止，按先子后父的顺序删除，避免每次只去掉最外层导致缓存持续累积。

按管理员要求，服务器只保留最近 **3 份完整可回滚备份**。`deploy/subscriptions-retention.py` 默认只预览，传入 `--apply` 才删除；保留运行镜像、三份备份的 `previous-image.txt` 所需镜像及相应源码目录，所以正常为 3 份备份和 4 个发布/镜像版本（当前版本加三份回滚依赖）。任意现存容器引用的镜像也受保护。旧备份、旧发布目录、根目录重复源码包/Git bundle 和过期 vm2api 镜像会清理，运行数据、槽位、配置、登录资料及其他服务不在清理范围。
